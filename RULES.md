# ПРАВИЛА РАЗРАБОТКИ YupDar — ЧИТАТЬ ПЕРВЫМ

Этот файл — обязательный к прочтению для ЛЮБОГО, кто трогает код YupDar
(человек или AI-ассистент). Читать ПЕРЕД каждым изменением. Правила ниже —
не рекомендации, а законы. Их нарушение уже приводило к тому, что у живых
пользователей «слетал» доступ и шёл поток жалоб.

Проектом управляет Светлана (автор). Разработчик исполняет её запрос — он не
владелец решений и не меняет продукт по своему усмотрению.

---

## ЗАКОН 1. Только то, что просили. Никакой самодеятельности.

- Делай РОВНО то, что в запросе. Не расширяй объём, не «улучшай» соседний код,
  не ужесточай поведение, не рефактори «заодно».
- Если по ходу задачи видишь ещё проблему — НЕ чини её молча. Опиши Светлане
  отдельно и жди её решения.
- Любое изменение, которое меняет УЖЕ РАБОТАЮЩЕЕ поведение для пользователей
  (в т.ч. «повышение безопасности», ужесточение проверок, смена правил доступа),
  делается ТОЛЬКО по прямой команде Светланы. Такое изменение = регрессия по
  определению, а регрессии — только по её личному указанию.
- Корень любой правки должен касаться исходного запроса. Уходить «вовне»
  (менять то, чего запрос не касался) — запрещено, кроме случая, когда задача
  прямо в том, чтобы развить что-то новое.

Проверка себя перед коммитом: «Меня об этом просили? Это изменит то, что уже
работает у людей? Если да — есть ли явная команда Светланы?» Нет команды — не делай.

## ЗАКОН 2. Ноль регрессий. Проверяй критический путь вживую.

Регрессия = сломалось то, что раньше работало. Чтобы их не было:

1. Прежде чем менять auth / доступ / оплату / что-либо на пути входа
   пользователя — выпиши ВСЕ штатные сценарии этого пути и после правки проверь
   КАЖДЫЙ вживую (curl к боевому API или локальный юнит-тест функции), а не «на глаз».
2. Для auth обязательный набор сценариев (все должны продолжать работать):
   - Telegram со свежим подписанным `initData` → доступ есть.
   - Telegram с подписанным, но устаревшим `initData` (долгая сессия) → доступ есть.
   - Telegram БЕЗ `initData`, но с положительным `initDataUnsafe.user.id`
     (перезапуск из истории, часть ссылок/кнопок) → доступ есть (см. ЗАКОН 3).
   - Гость в обычном браузере (отрицательный `_web_uid`) → работает как гость.
   - Админка (`/api/admin/*`) с неподписанным id → 401 (доступа НЕ даём).
   - Оплата (`/api/payment`) с неподписанным положительным id → identity не цепляется.
3. После деплоя — ОБЯЗАТЕЛЬНО дёрнуть боевой endpoint на реальном примере и
   убедиться, что ответ правильный. «Задеплоил» ≠ «проверил».
4. Каждый инцидент и его причину фиксировать в `BUGLOG.md`.

Инцидент-эталон (04.07.2026): PR ужесточил auth и стал отвечать 401 на
неподписанный положительный `x-telegram-id`. Но Telegram штатно шлёт такой id
при части способов открытия Mini App → у массы живых юзеров профиль перестал
грузиться → «всё заблокировано». Ужесточение было сделано без проверки штатного
сценария и без команды Светланы. Это нарушение ЗАКОНОВ 1 и 2 одновременно.

## ЗАКОН 3. Контракт системы доступа (не ломать).

Модель identity (`public/api/_lib/auth.js`, функции `getUser` / `requireUser`):

- Подписанный `x-telegram-init-data` (HMAC Telegram) — ДОВЕРЕННЫЙ путь. Подпись
  проверяется всегда.
- Отрицательный `x-telegram-id` — гость (`_web_uid`), само-владеемый анонимный
  аккаунт. Пускается как identity низкого доверия.
- Положительный `x-telegram-id` БЕЗ подписи — штатный Telegram-перезапуск без
  `initData`. Пускается как identity НИЗКОГО доверия ТОЛЬКО на нестрогих путях
  (профиль, контент, цены, промо). Управляется опцией `opts.strictId`:
  - `strictId` не задан (нестрого) → положительный неподписанный id ПРИНИМАЕТСЯ.
  - `strictId: true` (строго) → положительный неподписанный id ОТВЕРГАЕТСЯ (401).
- Строгие пути ОБЯЗАНЫ ставить `strictId: true` (через `requireUser(req,res,true)`
  или напрямую `getUser(req,{strictId:true})`):
  - Админка — `requireAdmin` → `requireUser(strict=true)`.
  - Деньги/скидки — `payment.js` (`getUser(req,{softInitData:true, strictId:true})`).

Никогда не «чини» жалобу на замки тем, что глобально режешь неподписанный
положительный id — сломаешь всех Telegram-юзеров без initData. И наоборот:
никогда не ослабляй `strictId` на админке/деньгах — это дыра подмены чужого id.

Модель тарифа/триала:
- Пробный доступ = РЕАЛЬНАЯ запись в БД (`access_level='premium'`,
  `subscription_plan='trial_7d'`, `subscription_end = now+7d`). Логика в
  `public/api/_lib/pricing.js` (`ensureTrialAccess`, `getTrialInfo`,
  `cleanupExpiredTrial`, `getEffectiveTier*`).
- `/api/user` отдаёт `access_level = getEffectiveTierWithSimulation(user, req)`,
  а не сырой `user.access_level`.
- Книга в триал НЕ входит: `canReadFullBook` для `trial_7d` возвращает false.
- Диагностика доступа делается запросом к БД и живым вызовом API, а НЕ
  списыванием на «кэш» и НЕ на пользователя.

## ЗАКОН 4. Два разработчика — синхронизация обязательна.

- Перед КАЖДЫМ `git push`: `git pull --rebase origin main`.
- CI после деплоя сам бампит `version.txt` / cache-busting токены отдельным
  коммитом `[skip ci]` → после деплоя снова `git pull --rebase origin main`,
  прежде чем продолжать.
- Оба разработчика читают этот `RULES.md` ПЕРВЫМ, до любого редактирования.
  Дополнять его — можно; ослаблять законы 1–3 — только по команде Светланы.
